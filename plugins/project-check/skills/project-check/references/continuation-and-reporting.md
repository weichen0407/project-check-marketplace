# 下一步建议与文档询问

Apply the [request language rules](response-language.md). For English requests, use the English prefix **[Project Check]** and the English report question defined there.

本规则覆盖「项目检查」插件的全部场景、MCP 与工具，遵守用户明确的输出格式
和是否继续／是否生成文档的选择。不要把建议当成用户已授权的新任务。

## 工具调用结束后

每次工具返回后，说明实际结果并给出 1–3 条与当前阶段有关的下一步建议。
同批并行调用可在结果到齐后合并列出，标明对应场景；在长流程中使用简短
进度说明，不必每个工具都发一篇完整报告。已经获准的流程可继续执行，不能
为了询问文档而额外中断；成本基线确认、关键问题选择等原有确认节点仍保留。

每条建议以 **【项目检查插件】** 开头，使用完整、可以复制为下一轮提问的
自然语言，写明目标场景或 MCP 的展示名称。例如：

- 【项目检查插件】确认这份成本基线，再用研发降本的价值工程方法分析。
- 【项目检查插件】基于刚才选中的创新方案展开详情，保留现有结构约束。
- 【项目检查插件】把目前已有结果整理成阶段报告，只输出实际涉及的章节。

根据实际阶段选择建议：

- 降本：流程说明 → 成本基线／BOM → 用户确认 → 方法分析 → 方案评估 → 报告。
- 创新：组件或因果分析后校准对象／选择关键问题；证据后生成方案；概念后
  选择并展开详情；详情后推荐验证、对比或按需进一步检查。
- 案例库：标准词后检索案例；案例后比较适用性、选择案例或按需转入创新。
- 调用失败：说明失败，推荐恢复连接／认证或继续独立可执行部分；不把失败
  当成无风险，不自动重跑、不擅自更换服务。

仅解释已有结果时，也推荐相关下一步，但不虚构本轮调用记录。不强制用户
补齐所有场景，不把当前范围以外的分析作为必做步骤。

## 每轮回答的结尾

插件相关回答完成后，追加一句：

**【项目检查插件】需要把当前已有结果整理成 Markdown、HTML 或 Word 报告吗？**

用户明确拒绝或要求暂时不再询问时，保持该偏好，直到用户重新提出。已经在
本轮生成文档时，交付文件并推荐可继续补充／更新的内容，不再重复询问是否
生成同一份文档。普通问答或插件开发说明不附加这套业务流程提示。

## 用户同意生成文档时

读取并遵循[阶段报告](../../project-check-report/SKILL.md)，使用插件 `templates/`
中的模板。单个 MCP、多个 MCP、只有聊天／资料或长上下文均可随时总结；没有
最少调用次数、固定生成时点或截止时限。仅使用当前模型可见的历史和材料。

只填已有事实、实际工具结果和有来源的分析；未涉及、未运行或缺失的字段及
章节标题不进入成品，一个方向完全没有内容时也不显示方向标题。不写“待补充”
“未检查”等占位结论，不推断为通过。报告范围和调用记录只列实际覆盖内容；
已知失败可如实写入失败记录。英文环境使用全英文模板和英文正文。
不为填满模板新增检索或重新分析。
